## Motion / transition / morph analysis (second pass, read-only)

Mapped every transition in the app. Three tiers, asymmetric maturity.

**Tier 1 — tab↔tab (Home/Library/Stats/More).** Routes form `topLevelRoutes` in
`androidApp/.../nav/FolioNavHost.kt`; `isTabMorph()` returns true when *both* ends are in that
set, which yields fade-only with `EnterTransition.None` for the slide. 220ms in, 180ms out.
`FolioNavShell.kt` carries the direction instead: a 420ms specular band (`navSweepBand` /
`navSweepAlpha` are pure functions) plus a stiffness-700 spring on the selected item's pill
width, icon size and tint. The comment explains the rejection of scale — scaling a page
re-rasterises every cover and glyph, so it goes soft then sharpens.

**Tier 2 — push/pop (~15 routes).** fade + slideInHorizontally, offset `it/24` in and
`it/40` out — i.e. a hair under 4% of width. Same 220/180ms.

**Tier 3 — in-place swaps.** `folioFadeSwap(motionEnabled)` in `components/EntryMotion.kt`:
`ContentTransform(fadeIn(180), fadeOut(120))`. Used by the Library shelf switch
(Books/Manga/Documents, `AnimatedContent` at `LibraryScreen.kt:967`) and the grid↔list↔compact
switch (`:1587`), same in `MangaLibraryScreen.kt`. `rememberSwapInFlight` + 
`FolioSharedElementsSuppressed` deliberately disable the cover morph for the 180ms cross
because two live copies of one shared key in one scope is undefined.

**The morph itself.** `SharedTransitionLayout` wraps the NavHost; `FolioSharedElements.kt`
provides the two scopes through `LocalSharedTransitionScope` / `LocalSharedElementScopes`
(CompositionLocals, so desktop gets null and everything is inert).
`Modifier.sharedElementOrNoop(key)` bails on `!motion || suppressed || scopes == null`.
Live call sites: book cover (LibraryGrid ×2, BookDetailHeader) and manga cover
(MangaLibraryItems ×3, MangaDetailScreen). Seeds already exist.

**Concrete gaps found (in priority order)**
- G1. `FolioSharedKeys.documentCover()` is declared and referenced nowhere. Documents have a
  full library shelf (with the Books/Manga/Documents switch) but NO cover morph into the
  document reader. Cheapest real win — the key and the mechanism already exist.
- G2. `sharedElement(...)` is called with the default bounds transform. The 1.7.3 API exposes
  the full form `sharedElement(state, animatedVisibilityScope, boundsTransform)`.
  Compose's own recommended morph (ComposeAnimationsCodelab) is 450ms / FastOutSlowIn and
  **linear** bounds — that is what gives the "grows while travelling" read the spec §13.6
  asks for. Right now travel and size share one default spring, so the plate reads as a
  crossfade with movement rather than a morph.
- G3. No `AnimatedContent` per-element `transitionSpec` anywhere: title and author hard-swap
  while the cover flies. `AnimatedContentTransitionScope` inherits `SharedTransitionScope`,
  so the cover applies from inside and text pairs with `Modifier.animatedContentOrNoop()`.
- G4. Only covers morph. Zero text pairing: library row title → detail headline, author,
  progress %, chapter label, manga chapter count. All have exact source/target pairs.
- G5. Morphs are only wired for library→detail. Home's shelf cards and manga history rows
  navigate to the same detail/search routes without a morph.
- G6. Desktop opts out entirely: no `SharedTransitionLayout` in `desktopApp/Main.kt`, and
  its nav is a manual `navStack` with `EnterTransition.None togetherWith ExitTransition.None`
  — hard cuts on every screen change. A desktop equivalent would be `SharedTransitionLayout`
  inside the existing `AnimatedContent`.
- G7. `MotionCapabilities.desktop.actual` hardcodes `rememberMotionEnabled() = true`, so
  desktop cannot honour OS reduce-motion even where it does animate.
- G8. No test covers transitions: `EntryMotionTest` only tests `chartStagger`.
  `NavigationTest` (androidTest) asserts routes and back behaviour, not motion. Nothing
  asserts the tab transition has no scale, that morphs are suppressed mid-swap, or that
  reduce-motion yields a plain fade.

**Rule 1 trap for any fix**: M6 work must not move `FolioNavHost`/`NavShell` into
`shared/src/composeUi/`. The morph machinery belongs in composeUi (already correct) but tab
definitions and the nav host are Android-only by the spec's Rule 1.

## Morph implementation — G1–G5 + G8 done (user excluded G6/G7)

Implemented all approved gaps. `:shared:compileKotlinDesktop`, full `:shared:desktopTest`,
and `:androidApp:assembleDebug` all green. No device testing yet.

**Stepwise commit shape used** (infrastructure → wiring → tests), which is what kept each
compile round to one or two errors:
1. `FolioTokens.motionMorph = 450L` (`theme/Theme.kt`, beside `motionEmphasis`).
2. `components/FolioSharedElements.kt` — the whole core of the change:
   - `folioMorphBounds`: `BoundsTransform { _, _ -> tween(motionMorph, FastOutSlowInEasing) }`.
     Replaces the API default **spring** (Rule 6 bans springs in navigation; a spring's settle
     time is distance-dependent, so a short hop and a full-viewport flight would land at
     different moments and the paired text would drift off its own cover).
   - `sharedElementOrNoop(key, boundsTransform = folioMorphBounds)`.
   - **`sharedTextOrNoop`** — new, built on `Modifier.sharedBounds`, NOT `sharedElement`. The
     two copies of a title are never the same size, and `sharedElement` interpolates *content*
     (drags glyphs through a scale); `sharedBounds` keeps both composed and cross-fades while
     only the box interpolates.
   - `rememberMorphAttachment()` — one private gate both modifiers call, so a cover and its
     paired title can never disagree about whether a morph is running.
   - New keys: `bookTitle/bookAuthor/mangaTitle/documentTitle`.
3. `suppressFallbackText` threaded `FolioCoverPlate` → `BookCover` → `FallbackCover`.
   `suppressFallbackCaption` on `DocumentThumbnail` (now `internal`, reused by the doc reader
   landing). This is the double-text fix: without it the generated fallback draws the same
   title at a second size for the length of the morph.
4. `FolioNavHost.kt`: `FolioSharedElementScope(this)` now also wraps STATS, READER,
   DOCUMENT_READER, MANGA_READER, MANGA_HISTORY.
5. Reader landings. Manga + document are unconditional (pure Compose both platforms).
   **EPUB is opt-in** behind new `ReaderSettings.morphIntoReader` (off by default), with a
   toggle in `SettingsPanelReading`. Reason: Android is `WebView`-in-`AndroidView` (Compose
   *can* composite above, cannot observe paint timing → possible one-frame seam); desktop is
   JCEF `SwingPanel` (impossible). `ReaderScreen` drops the plate as soon as `chapterHtml`
   arrives.
6. Source keys attached: LibraryList (`BookListItem` + `BookCompactItem` — neither had any key
   before), LibraryGrid text pairing, HomeScreen ×3 plates, MangaHistoryScreen, MangaDetail,
   MangaLibraryItems grid+list, DocumentLibraryItems grid+list.
7. `folioFadeSwap(motionEnabled, sizeTransform = null)` + pure
   `folioSizeTransformEligible(itemCount) = itemCount in 1..8` + `folioSwapSizeTransform()`
   (`SizeTransform(clip=false)`). Applied at all three swap sites. Disabled under reduce-motion
   inside `folioFadeSwap` itself.
8. `docs/FOLIO_MOTION_SPEC.md` §13.6 amended with a v1.3 subsection.

**Gotchas hit, worth remembering:**
- **`@file:OptIn(ExperimentalSharedTransitionApi::class)` is per-file.** Adding a
  `sharedElementOrNoop` call to a new file fails the build until that file opts in. Hit it in 7

  ReaderScreen).

  `descriptor.elementsCount == baseJson.size`** on a hand-written `nonDefaultRow()` fixture.
  Every new `ReaderSettings` field MUST be added to that fixture or the test fails — it caught
  `morphIntoReader`. Good test; expect it every time.
- `DocumentLibraryState`'s list field is `items`, not `documents`.
- `gradlew ... | tail -N` hides `e:` lines; pipe through `grep -E "^e: "` instead.

**Deliberate non-changes:**
- `morphIntoReader` is app-level: NOT in `ReaderSettings.copyWith`/`toBookSettings` and NOT in
  `ALL_INHERITED_FIELDS` (`androidApp/.../settings/SettingsInheritance.kt`). It's a
  device-confidence flag, not a reading preference — it must not vary per book.

### Corrections after tracing call sites (don't repeat my first guesses)

I initially flagged `stats_exclusions` and `revisit_items.resolved_at` as "unfinished intent".
**Both are wrong — fully wired and well built:**
- `stats_exclusions` → `StatsExclusionRepository` (interface) + `JdbcStatsExclusionRepository` +
  `StatsScope` resolver + `JdbcStatsExclusionRepository.observeExclusions()` consumed by BOTH
  `StatisticsViewModel` and `HomeViewModel`. `StatsScope.kt` is a genuinely thoughtful design
  (one-way group exclusion, `hasRules()` short-circuit to skip 2 roundtrips/book on large
  libraries, `expandExtensionExclusions` to map extension pkg → numeric source id).
  Tested in `CoreSampleTest` / `HomeMangaCardsTest` with `FakeExclusionRepo`.
- `revisit_items.resolved_at` → `RevisitItemsScreen` calls `resolveRevisitItem`;
  `JdbcAnnotationRepositories` implements it; `SyncEngine` does real conflict resolution
  (adopts remote resolvedAt when local is unresolved, resolves locally when remote is).
  Unresolved query is `WHERE resolved_at IS NULL ORDER BY created_at DESC`.

**Real finding — `estimateReadingTime` uses a hardcoded 220 wpm.** In
`ui/book/BookDetailHeader.kt:280`. Meanwhile `BookStatistics.averageReadingSpeedWpm` IS
computed (`StatisticsModels.kt:53`, `(wordsRead / minutes)`) and persisted
(`JdbcStatisticsRepository` col `average_reading_speed_wpm`). So the app measures your actual
reading speed and then estimates with a made-up constant. This is the cheapest high-value fix
in the codebase: same formula, swap the constant for the user's measured speed.

**Real finding — `BookStatistics.addSession` is DEAD CODE with a stub inside.**
`StatisticsModels.kt:39`. No callers anywhere (only `ReadingCycle.addSession` in
`ReadingPosition.kt:178` is different). And its private helper is:
```kotlin
private fun calculateReadingDays(session: ReadingSession): Int {
    // Simplified - in reality would track unique dates
    return readingDays
}
```
i.e. `readingDays` never advances. Since the function is uncalled, nothing is broken *today* —
but it's a loaded gun: it looks like the canonical way to fold a session into book stats, and
wiring it up would silently produce a wrong `reading_days` column. Either port the real
unique-date logic (the `daily_statistics` table already has per-day rows to derive it from) or
delete it.
- Related: `book_statistics` has `average_reading_speed_wpm` / `reading_days` columns and

## Three perceived-lag fixes (reported symptoms: stats loads abruptly, manga flashes a
## wrong category, bottom nav background renders late)

All three were real and each had a **different** root cause. Fixed in one pass, 41 files
touched in the working tree overall.

**1. Stats loaded abruptly — `collectAsState(initial = StatisticsUiState())`.**
`StatisticsViewModel.state` is a `combine` of four suspense queries (a year of sessions,
currently-reading, finished, whole library) plus, when exclusions are wired, **two roundtrips
per book** to resolve tags/collections. For that whole window the tab painted a *zeroed* state —
including the "Nothing measured yet" card — then every value changed at once.
- Added `StatisticsViewModel.ready: Flow<Boolean>` derived as `state.map { true }.onStart { emit(false) }`
  — derived from `state` rather than a separate flag so it cannot disagree with the emission
  it describes. Needed a new `onStart` import.
- New `ui/statistics/StatsSkeleton.kt` (~185 lines) modelled on the existing
  `ui/home/HomeSkeleton.kt` precedent, reusing `FolioShimmer`'s primitives
  (`FolioSkeletonBlock`, `FolioSkeletonLine`, `rememberShimmerPhase`). Measures lifted from the
  real screen: `heroBleed` + the same asymmetric padding for the overture, the **96dp circle**
  for the goal dial (a rounded rect there reads as a different component), `spaceBeat` around
  the rule, `gutter` headings, `weekChartHeight` inside an `edgeStart` well.
- `StatisticsScreen` gates with `if (!ready) { Box(padding(top = LocalFolioTopInset.current)) { StatsSkeleton() }; return }`.
  The early `return` is **after** every hook (collectAsState/remember/LaunchedEffect), so
  composition is stable across the transition. The skeleton carries the same top inset so the
  first real frame does not jump.

**2. Manga flashed the wrong category — `selectedCategoryId` opens `null`.**
`MangaLibraryViewModel.selectedCategoryId = MutableStateFlow<String?>(null)`, and **null means
"no membership filter"** → the shelf's first frames render the *entire* library, then the
remembered category (`KEY_LIBRARY_CATEGORY`, read via a *suspend* `settingsRepo.getRaw`)
restores and it snaps. `ready` cannot catch it: `ready` tracks whether `library` has emitted,
and the unfiltered list is non-empty so `visible.isEmpty()` is false and the grid draws.
- Added `MangaLibraryViewModel.categoryReady: StateFlow<Boolean>` =
  `combine(selectedCategoryId, categories) { selected, list -> selected != null || list.isEmpty() }`
  — also true when there are *no* categories, because waiting there would hang the screen.
- `MangaLibraryScreen` gained a branch **above** the `!ready` one, exempting
  `isSelectionMode` and `searchActive` (both user-initiated, with their own list semantics).

**3. Bottom nav background rendered late — `suppressBlur` only moved the fill alpha.**
`FolioNavShell` already had a 120ms post-route-change `suppressBlur` workaround, and its comment
describes the symptom almost verbatim. But it only fed `capsuleFill`; the `.folioVeil(...)` call
was passed nothing, so `folioVeil` independently recomputed `caps.blur && backdrop != null`
(**still true**) and kept blurring the *stale* backdrop — the outgoing screen's layer. Fill
arrived on time, material behind it was a frame old.
- Extended `GlassSpec` (`components/Glass.kt`) with `blurEnabled: Boolean = true` + a doc
  explaining it is a per-surface *effect* toggle, not a capability toggle. Defaulted, so the
  existing `GlassSpec(blurRadius = 60.dp)` call site still compiles.
- `folioVeil` now computes `val blurred = caps.blur && backdrop != null && glass.blurEnabled` —
  one boolean read by both the blur layer and the fill tier, so they can never disagree.
- `FolioNavShell` passes `glass = GlassSpec.Default.copy(blurEnabled = !suppressBlur)`.

**Tests (8 new, all passing):**
- `GlassCapabilityTest` +3: `a surface can hold its blur off while the backdrop is stale`,

**Gotcha — `SharingStarted.Lazily` StateFlows need a collector in tests.** My first two manga

Lazily, ...)` flow produces **nothing** until something collects it, so `.value` stays at the
initial value forever. Fix: `val collector = launch { vm.categoryReady.collect {} }` … `finally
{ collector.cancel() }`. The pre-existing `libraryRestoresLastViewedCategoryAndPersistsSelections`
test passes because it reads `selectedCategoryId`, a plain `MutableStateFlow`, not a derived one.

**Gotcha — device coordinates vs. displayed screenshots.** `adb exec-out screencap` on this
OnePlus returns native **1080×2392**, but the image shown back is downscaled to ~540 wide. Read
tap coordinates from the native size. Best source of truth: `adb shell uiautomator dump` +
`content-desc="..." bounds="[x1,y1][x2,y2]"` — the bottom nav icons live at y≈2196–2259

## Home cold start: the manga side no longer gates `loaded`

**The complaint.** Not tab-visit reloading — *"the first load itself for home is too long"*,
app restart. The staging warmth added earlier does nothing for this, because on a cold start
every eager flow begins from zero.

**Root cause.** `HomeViewModel.build()` resolved the §11.4 manga cards **inline, in sequence,
before it could return**, and `loaded = true` sits at the very end of that function. The serial
chain was: `getNewChapterBadges` → `buildMangaContinue` (progress, unread counts, manga statistics,
recent history, then a per-row `mangaRepo.get` + `categoriesFor` + `sourceWebUrl`) → a **second**
full `mangaRepository.observeLibrary().first()` purely to answer "is the library non-empty?".
None of it feeds the reading ring, the streak or the Continue-reading shelf.

**Fix.** `build()` now takes a `MangaSections` parameter and reads the three fields off it. A new
`mangaSectionsFlow(exclusions)` resolves them; `state` emits **twice per exclusion set** —
`EMPTY` first so the book pipeline is never held, then the resolved sections. Deliberately *not* a
`combine`, since a combine waits for both sides, which is the dependency being removed.

`runCatching` wraps each manga call, so a manga-side failure degrades to empty cards rather than
taking down Home's numbers — the sections are additive.

**Two things I nearly got wrong, worth remembering:**
1. I first "optimised" `hasManga` to `mangaContinue.isNotEmpty()`. That is a **behaviour change**,
   not an optimisation: `mangaContinue` is capped at 3 and filtered through `StatsScope`, so a
   manga-only library with everything excluded would have flipped Home into its book-only shape.
   Reverted. `hasManga` genuinely asks a different question and its own read had to move off the
   path instead of being replaced.
2. My first `sections` flow read exclusions with a one-shot `.first()`, which would have **frozen
   the exclusion set for the process lifetime** — the reader can toggle exclusions on Stats and
   Home must re-gate its cards. Now driven by `observeExclusions()` through `flatMapConcat`.

**Proven, not assumed.** `HomeColdStartTest` (2 tests) gates the manga repo behind a
`CompletableDeferred` and asserts `loaded = true` arrives while the manga side is still silent.
I temporarily restored the pre-split inline code and confirmed **both tests fail with
`TimeoutCancellationException`**, then restored the fix. The tests detect the regression; they are
not vacuous.

## `FolioNavModelImpl`: a `by lazy` ordering crash that killed the app on frame one

Installing the release exposed this immediately:

```
java.lang.NullPointerException: Attempt to invoke interface method
    'java.lang.Object kotlin.Lazy.getValue()' on a null object reference
```

## Home cold start: the 7-second skeleton was extension loading, not a query

Measured on device (release build, 3 extensions installed). Home's `loaded` went from
**+7,245ms to +128ms**, and `am start -W` TotalTime from ~1,500-1,875ms to 567-993ms.

**How it was found.** Guessing had failed three times, so I instrumented instead: a temporary
`HomeStartupProbe` (`mark(label)` on every input source and around `build()`) plus a
`DbLockProbe` around `Database.withConnection`. The stage dump named it in one run:

```
+155ms   exclusions raw (5)          <- observeExclusions() emitted
+7239ms  exclusions expanded         <- 7,084ms spent here
db lock: 73 acquisitions, 3436ms total wait, worst hold 177ms
```

The lock probe matters: it **ruled out** the mutex contention theory (a plausible-looking
`withConnection` global lock) before I spent time on it. The wait was in the flow, not the queue.

**Root cause.** `expandExtensionExclusions(rows, sourcesFlow.first())` ran *before* the first
emission, and `sourcesFlow` is `MangaBackend.observeSources()` — on Android,
`ExtensionManager.installedExtensionsFlow`, which is

```kotlin
onStart { initialized.await() }.map { it.values.toList() }
```

i.e. **a flow that emits nothing until the whole extension runtime has finished loading** (disk
scan + dex classload of every installed extension APK). So the first frame of Home was gated
behind extension loading, for a source-id mapping that is a no-op unless an EXTENSION-scoped
exclusion exists, and that the book pipeline never consults.

**Fix.** The expansion moved inside `mangaSectionsFlow` (where the source list is needed anyway);
the base emission now carries the **raw** exclusion rows. That is correct, not merely expedient:
an EXTENSION row names an extension package and no book can match one, so gating books on the
unexpanded set is exact — only manga sections need the expansion.

**The second site, found by the test rather than by the device.** `discoverFlow` is combined into
the *outer* flow that produces `state`, and its `currentExclusions()` also did
`backend.observeSources().first()` on the path of the first value. On device the second emission
raced ahead and the measured 128ms looked fine; the test with an honestly-hung source list still
timed out. Now the cache is keyed on the **raw** rows and the expansion happens inside
`fetchDiscover`, after the first emission.

**Guards.** `HomeExtensionGatingTest` (2 tests) — a `MangaBackend` whose `observeSources()` never
emits must not delay `loaded`, and direct BOOK exclusions must still gate the first emission.
Verified non-vacuous: both fail with `TimeoutCancellationException` against the reverted code.

**Removed.** All diagnostics (both probes, the expect/actual pair, the `withConnection` wrapper).
Note `commonJvm` cannot reference `android.*` for the desktop target — a `try { android.util.Log }
catch` does not compile there, so a probe living in `commonJvm` has to avoid it entirely.

**Unrelated but surfaced by the lock probe:** `MangaDownloadManager.resumeInterrupted` held the
database mutex for 135ms during startup. Not gating Home; worth a look on its own.

## The ambient light's clock had a units bug — and the morph suppression was the wrong fix

Two separate mistakes, both mine, both from the same afternoon's work on "the home→library morph is laggy".

### Mistake 1 — `rememberSlowPhases` mixed nanoseconds with milliseconds

Replacing §17's `rememberInfiniteTransition` with a throttled clock (to stop the app redrawing every
vsync forever) I wrote `elapsed % period` where `elapsed` came from `withFrameNanos` (**ns**) and
`period` from `AMBIENT_PERIODS_MS` (**ms**). So the modulo wrapped every 47 **microseconds** instead
of every 47 **seconds**: every 100ms tick landed on an arbitrary point of the cycle and the light
**strobed** instead of drifting. The user reported it precisely — *"youve made the light animation
too fast and bad, make it slow and restore"*.

Fix: `elapsedMs = (now - origin) / NANOS_PER_MS` before the modulo. Also extracted the pure
`slowPhaseAt(elapsedMs, periodMs)` so the *rate* is testable, and added three tests to
`AmbientLightTest`: `phaseCompletesExactlyOneTurnPerPeriod`,
`slowClockTicksAdvanceThePhaseByASmallFixedStep` (pins the step at 0.0134 rad and asserts the raw
nanosecond input is *not* a valid ms elapsed time — i.e. it fails loudly if the units regress), and
`slowClockNeverHoldsTheFrameLoopOpen`. All 498 desktop tests pass.

**Lesson:** a clock is the one thing you cannot eyeball. Any `withFrameNanos` value that meets a
duration constant needs the unit in the variable name.

### Mistake 2 — I "fixed" the laggy morph by deleting the morph

The user's original words were *"the morph animation from home to library is laggy fix"*. I
diagnosed that Home's shelves and the Library's grid publish the same `book_cover:<id>` keys, so the
registry paired them across a tab switch and flew every shared cover across the viewport — and
concluded the morph itself was the problem. So I added `FolioTabMorph` (a nav-layer gate armed on
the tab tap, holding `morphsSuppressed = true` for `motionStandard + 120`ms) and disabled tab↔tab
cover morphs entirely. Deleted it today.

The user's reaction, twice: *"why cant i see any morph animation"*, then *"i cant see the morphs yet
again wtf"* → *"i wanted u to fix the lag not remove the morphs"*.

**The measurement already said the morph was innocent.** `dumpsys gfxinfo … framestats` across six
tab switches: `handleInputStart → drawStart` (all UI-thread work — anim, measure, layout, draw) was
**0.58 ms**; the cost was `issueDrawCommands → swapBuffers` (~6.4 ms, render thread) and
`swapBuffers → frameCompleted` (~6.8 ms, present). The app was **draw-bound and present-bound**, and
it rendered ~118 frames / 4s **at rest** because §17's ambient light and §13.4's hero mesh were
re-sampled every vsync while a full-screen `folioField` read the ambient in its draw phase. Disabling
motion made it render **zero** frames — proving the ambient was the *only* thing keeping the loop
alive. The morph was never the cause.

**Lesson (the expensive one): when a user says "X is laggy", the fix is almost never to remove X.
Measure which stage is slow before touching behaviour, and never trade away a feature the user asked
for in exchange for a performance win they did not ask for.** Corollary: my "it's fixed" check after
the reduce-motion incident verified *frame counts*, not morphs — a proxy for the wrong thing. Verify
the exact thing the user reported.

deliberately draws one frame per **100ms**, so a 30ms frame misses nothing. Jank is only meaningful
during a transition, where frames must be consecutive.

What the table says: **the UI thread does 1.4ms — recomposition/layout/draw-record is NOT the
bottleneck.** The cost is render (5.8–7.8ms) + present (8.3–11ms) ≈ 14–19ms per frame, i.e. this UI
cannot currently draw faster than ~40–50fps, and the transition runs at ~41fps with occasional
70–163ms hitches (the 163ms on Home→Library is almost certainly the Library grid's cover decode).
Note idle render (12.65ms) is *more* expensive than transition render (7.81ms) — the transition
already has `suppressBlur` active for its first 120ms, which is weak evidence that Haze blur is a
real per-frame cost worth suppressing across the whole transition.

**Still to do on the lag:** the remaining cost is the full-screen `folioField` redraw plus the glass
blur. Candidates, in order: extend `FolioNavShell`'s `suppressBlur` window to cover the whole
transition; cache the atmosphere as a static layer instead of redrawing it per frame; pre-warm the
Library covers to kill the 163ms hitch.

### Tooling gotchas that cost real time here

- `dumpsys gfxinfo … framestats` rows are **comma-separated**, so awk needs `-F,`. Without it every
  row is a single field, `NF>=24` fails, and every measurement silently reports `n=0`. I documented
  the FS requirement in a comment and then still forgot to pass the flag — twice.
- Rows have a **trailing comma** (NF=25 for 24 columns).
- Incomplete frames appear with `$17`/`$18` = 0, which produces **negative** durations. Guard with
  `$17 > 0 && $18 > $17`.
- `Total frames rendered:` from a plain `dumpsys gfxinfo <pkg>` (sampled twice, no `reset`) is a
  robust cross-check that needs no parsing at all.
- `screenrecord` is blocked on this device, so morphs cannot be filmed — morph presence has to be
  established by reading the code, not by observation.

## The remaining transition lag is Haze's backdrop capture, not the blur

Isolated by toggling **Settings → Transparency → "Liquid glass effects"** off on the device and
re-measuring the same three switches (no rebuild needed):

| transition | glass ON avg | glass OFF avg | render | present |
|---|---|---|---|---|
| Home→Library | 27.0ms | **16.2ms (−40%)** | 7.81 → 5.15 | 9.39 → 4.87 |
| Stats→Home | 23.4ms | **18.4ms (−21%)** | 7.42 → 5.34 | 8.33 → 6.16 |
| Library→Stats | 21.7ms | 21.2ms | ~unchanged | ~unchanged |

`>1.5x interval` frames on Home→Library fell from 92.4% to 24.6% — frames start making their vsync
deadline. (Restore the toggle to ON afterwards; the opacity sliders are Top bar 88% / Navigation bar
37% / Cards and sheets 64%.)

Splitting the cost *within* a transition: frames 1–3 already had the blur **effect** suppressed by
the capsule's existing 120ms `suppressBlur` while the backdrop **source** was still recorded → render
~10.7ms. With the effect back on → ~12.2ms. With everything off → ~5.2ms. So:

- `hazeSource` backdrop capture (attached to every screen via `folioBackdropSource`) ≈ **5.5ms/frame**
- `hazeEffect` blur ≈ **1.5ms/frame**

The capture is the cost. During a transition **two** pages are composed, so it was being paid twice
per frame, for a cross-fade in which the glass above is barely legible.

### Fix: `FolioGlassTransitionHold` (Glass.kt) + one hoisted window in the shell

- `Glass.kt`: `FolioGlassTransitionHold(suspended, content)` provides `LocalGlassBackdrop = null`
  while suspended. Expressing the hold as *no backdrop* rather than a new flag means every consumer
  ([`glassBlurred`], [`folioBackdropSource`], [`folioVeil`]) already reads it and walks down to the
  **designed** non-blur fill together. A flag would have to be threaded into each consumer, and any
  consumer that missed it would paint a blur-tier fill over an absent source — the exact text
  bleed-through the blur exists to prevent. The provider is always emitted (only its value changes)
  so toggling never disposes the wrapped subtree, which for the nav host would drop saved back-stack
  state.
- `FolioNavShell.kt`: hoisted the transition window out of the capsule to `glassHold`, sized
  `glassTransitionHoldMs = motionStandard + 80` (300ms), and used it for **both** the destination
  (wrapped in the hold) and the capsule (`capsuleFill` + `glass.blurEnabled`). The old flat 120ms was
  *shorter than the 220ms enter*, so the material came back mid-transition over exactly the moving
  backdrop it was being held off for — a correctness bug as well as a perf one. `GlassCapabilityTest`
  now pins `glassTransitionHoldMs > motionStandard`.

**Verified on device** (release build, two runs each):

| transition | before | after (hold) | glass-OFF floor |
|---|---|---|---|
| Home→Library | 27.0ms, render 7.81, `>1.5x` 92.4% | **21.5 / 21.6ms**, render 5.2–7.6, `>1.5x` 49–59% | 16.2ms |
| Stats→Home | 23.4ms, render 7.42, `>1.5x` 62.5% | **16.5 / 18.2ms**, render 4.2–5.0, `>1.5x` 39–40% | 18.4ms |
| Library→Stats | 21.7ms | 20.0 / 22.2ms (unchanged) | 21.2ms |

So ~20–25% off two of the three, with render reaching or beating the glass-OFF floor on Stats→Home.
Idle is unchanged at 9.9 fps, as it should be — the hold only applies to transitions. Library→Stats
was unmoved by both this and the glass toggle, so its cost is elsewhere (Stats' own charts, not glass).

The gap to the floor is `present` (8.3ms vs 4.9ms), i.e. frames still miss vsync — the remaining
expensive frames are the ambient field's 12.65ms redraws, which still land ~4 times during a
transition. Freezing the ambient for the transition window is the next obvious step, but it needs a
second CompositionLocal threaded into `rememberSlowPhases`.

Also fixed while here: `MangaReaderProgressTest`'s `FakeBackend.pageListFetches` was a plain
`mutableListOf` appended from concurrent coroutines, so it intermittently **lost entries** —
`openPublishesCurrentChapterBeforeNeighbours` failed once with `[/c2, /c3]` (the first write lost),
which reads like a product bug about fetch ordering and is not one. Now a `ConcurrentLinkedQueue`.
That flake failed a whole release build, so it was worth the two lines.

**Visual tradeoff to watch:** the capsule now shows its designed fill for the whole transition (300ms)
instead of 120ms. That is the same fallback it already used, just for longer.

## CORRECTION — the glass transition hold was REVERTED, not kept

The entry above is wrong to leave standing. `FolioGlassTransitionHold`, `glassTransitionHoldMs` and
the `glassHold` wiring were all **removed**, along with the `GlassCapabilityTest` case that pinned

exactly the mistake that was made here.

**Lesson:** the ~5ms/frame `hazeSource` capture is real and was measured (see the isolation table

## The cold-start Home→Library morph: root cause, and a measurement trap

### First, the trap — a whole round of measurements was measuring the wrong screen

My first cold-vs-warm probe tapped the Library tab at `(520, 2016)`, read off a scaled screenshot.
That y is **not** the nav bar: it lands in the shelf above, so every one of those runs was
*opening a book* and measuring Home→Reader, not Home→Library. The numbers looked plausible (a big
recomposition stall appeared exactly where a first composition should be), which is what made it
dangerous — they were wrong in *target*, not in *shape*.

**Take tap coordinates from `uiautomator dump`, never from a screenshot.** The real bottom-capsule
touch targets on this device (1080x2392) are:

| tab | bounds | tap |
|---|---|---|
| Home | [218,2199][275,2256] | 300, 2227 |
| Library | [482,2196][545,2259] | 513, 2227 |
| Stats | [644,2196][707,2259] | 675, 2227 |
| More | [806,2196][869,2259] | 837, 2227 |

```
adb shell uiautomator dump /data/local/tmp/ui.xml
adb shell cat /data/local/tmp/ui.xml | tr '>' '\n' | grep -iE 'home|library|stats|more'
```

Two more adb gotchas from the same round: `adb pull` needs a **Windows** path (`D:/...`), not the
Git-Bash `/d/...` form — and `/sdcard` is not writable by the `shell` user here, so write captures to
`/data/local/tmp` instead. `adb exec-out screencap -p > file` does accept the bash path.

### Finer `framestats` column map (verified against the header line)

The dump's own header, which is authoritative:

```
Flags,FrameTimelineVsyncId,IntendedVsync,Vsync,InputEventId,HandleInputStart,AnimationStart,
PerformTraversalsStart,DrawStart,FrameDeadline,FrameStartTime,FrameInterval,WorkloadTarget,
SyncQueued,SyncStart,IssueDrawCommandsStart,SwapBuffers,FrameCompleted,...
```

So awk field N == header field N, and the useful splits are:

| split | meaning |
|---|---|
| `$8-$7` | AnimationStart → PerformTraversalsStart = **animation callbacks + recomposition** |
| `$9-$8` | PerformTraversalsStart → DrawStart = **measure + layout** |
| `$15-$14` | SyncQueued → SyncStart = render-thread queue wait |
| `$16-$15` | SyncStart → IssueDrawCommands = **render-thread work** |
| `$6-$3` | IntendedVsync → HandleInputStart = **UI thread was still busy** (the tail of the *previous* frame's work, so it double-counts the stall) |

### The root cause

Measured Home→Library, correct target, ~2s per run, release build:

| run | n | avg | worst | UI | render | present |
|---|---|---|---|---|---|---|
| cold (tap 1.5s after launch) | 82 | 32.0ms | 134.5ms | 2.39 | 9.70 | 6.42 |
| cold, app idle 8s before the tap | 66 | 36.3ms | 126.4ms | 2.85 | 10.27 | 5.52 |
| warm (2nd visit, same process) | 75 | 27.8ms | 74.3ms | 1.93 | 9.53 | 5.53 |

Waiting 8s before tapping changed nothing — so this is **not** startup CPU contention. Totalling the
run, the cold-specific extra is **~230ms of `wait` + ~55ms of `recompose`**, i.e. all UI thread.
`layout` is ~8ms for the whole run; GPU is not the differentiator.

Per-frame, the cold run starts *smooth* (frames 4–24 at 11–20ms) and then blows up at frame 25+
(~280ms in): recompose 27.6ms, then 66/88ms of blocked UI thread. ~280ms is when the shelf read
lands. The mechanism:

- `LibraryViewModel` is `by lazy` and **not** in `warmTabState()`, so the shelf read only starts when
  the Library destination first composes.
- `LibraryScreen` shows `LibrarySkeleton` while `books == null`, then swaps to the real grid in one
  composition pass when `filteredBooks` first emits.
- `libraryShelfSeed` was written to prevent exactly this — but its input, `allBooks`, is a
  `collectAsState(initial = emptyList())` **inside the screen**, so it is always empty on the
  destination's first frame. The seed could never fire. It was dead code in practice.
- So the grid's first composition lands in the *middle* of the morph, and on a cold process that
  composition is also cold-code. Warm visits compose it too, just ~40ms in and JIT-warm (35ms of
  recompose spread over frames 4–7), which is why they look smooth and why relaunching brings it back.

### The fix

1. `FolioNavModelImpl.libraryBooks` — a `StateFlow` collected `SharingStarted.Eagerly` from app start,
   touched in `warmTabState()` alongside `homeState` and `statisticsVM`. The Library was simply the
   one tab missing from the existing warm-up.
2. `LibraryScreen.knownBooks` — read as a **`StateFlow`**, because the seed is the argument to
   `collectAsState`, which only delivers a flow's value on the frame *after* the first composition.
   Seeding from a collected value would put one frame of skeleton back inside the morph. The current
   value is read synchronously via `libraryShelfSeedFrom`.
3. `remember`ed the shelf flows. `viewModel.allBooks()` / `allSeries()` / `filteredBooks(state)` each
   return a **new Flow per call**, and they were called inline in composition — so every recomposition
   of `LibraryScreen` tore down and resubscribed `collectAsState`, i.e. a fresh database read per
   recomposition. `filteredBooks` is now keyed on the `LibraryState` it is built from.
4. `rememberCoverAccent` samples on `Dispatchers.Default`. `sampleFromBitmap` does
   `bitmap.toPixelMap()` — a full-bitmap `IntArray` + `readPixels` — and `LaunchedEffect` runs on the
   composition's dispatcher (the UI thread). A shelf composes a dozen covers at once and
   `awaitCoverBitmapForAccent` polls on a 100ms tick, so the samples land together. Measured as a
   ~10ms recompose spike late in the transition — real, but *not* the headline.
5. `BookCover` used `rememberEntryProgress` (composition-phase) for its 260ms reveal, so every cover
   recomposed **per frame** through the part of the morph the reader is watching. `rememberEntryState`
   is the draw-phase form `EntryMotion` documents for exactly this; now used.

### Still open (not fixed, deliberately)

- **render ≈ 9.5ms/frame in *every* run, warm or cold.** That is the Haze `hazeSource` capture
  (~5.5ms) paid twice because a transition composes two pages. The transition runs at ~37fps (27ms
  avg, 100% of frames over the 90Hz interval) even when warm. The obvious lever is standing the
  backdrop down during the transition — **already tried and reverted**, because it makes the bars
  visibly lose their glass. Do not retry it without solving that.
- **`present` ≈ 5.5ms**, attributed earlier to the ambient field's ~12.65ms redraws landing ~4× per
  transition. Freezing the ambient for the transition window needs a second CompositionLocal threaded
  into `rememberSlowPhases`.
- **Library→Manga has the same class of bug** as Library→Books had: `mangaLibVM` is `by lazy` and not
  in `warmTabState()`, so switching the shelf to Manga composes it cold. Not warmed because the reader
  did not report it and it adds launch cost unverified.

## CORRECTION to the line above, and a sharper finding: the Manga VM fires I/O on the *Books* shelf

The paragraph above was written from a bad grep. It said `MangaScreensCommon.kt:183` renders
`FolioCoverRailSkeleton(count = 4)` "while loading" and read that as the Manga shelf's skeleton. It is
not: that line is inside `GlobalSourceSection`, the *search-results* rail. The Manga shelf's own
loading state is `LoadingPlaceholder` in `MangaLibraryScreen.kt:205/212`, gated on `categoryReady` and
`ready` — a deliberate design, not an oversight. Lesson: read the enclosing composable before claiming
a skeleton is "the shelf's".

**The real finding.** `MangaLibraryViewModel` has two `init` blocks with side effects, and the Library
route forces its construction *in Books mode*, inside the Home→Library morph:

- `FolioNavModelImpl.kt:236` — `mangaLibVM by lazy { MangaLibraryViewModel(...) }`
- `FolioLibraryRoutes.kt:299` — `mangaLibraryViewModel = navModel.mangaLibVM` is a plain argument
  expression, so it reads the `lazy` and runs the constructor on **every** `LibraryRoute`
  composition, whatever `libraryMode` is. Nothing else touches it on a cold start
  (`MainActivity.kt:266` is inside `onBackWalked()`, only on back; `warmTabState()` never mentions it).
- `MangaLibraryViewModel.kt:178` — `scope.launch { categoryRepo.ensureSeeded() }`, and
  `JdbcMangaRepositories.kt:787` writes (inserts the Main category, shelves in-library manga).
- `MangaLibraryViewModel.kt:323` — `scope.launch { while(true) { updateLibrary(); delay(30min) } }`.
  The `updateLibrary()` call is **before** the first `delay`, so it runs immediately, and it loops
  every in-library manga doing `chapterRepo.getChapters()` (DB) + `backend.fetchChapterList()` (**network**).

So the first tap on Library — on the Books shelf — starts a DB write and a network pass across every
manga source, in the middle of the transition. `mangaVmScope()` is `Dispatchers.Default`, so the cost
is not direct UI work: it is **DB write-lock contention** (a write blocks the shelf's own reads, and
`libraryBooks` was just made eager) plus CPU/IO contention with cover decode, which is the morph's
biggest cost and shares `Default`/IO. That is a mechanism argument, consistent with the cold run's
+230ms of `wait` rather than `recompose`, but it is **not measured** — the device was gone.

**The cheap fix is a trap.** Passing `null` unless `libraryMode == MANGA` looks obvious and breaks the
screen: `LibraryScreen.kt:250–259` reads the manga selection flows *unconditionally* (not mode-gated),
through `remember { mangaLibraryViewModel?.isSelectionMode ?: MutableStateFlow(false) }` — keyed on
**nothing**. The first composition is in BOOKS mode (`libraryMode` starts BOOKS and is restored
async), so the `remember` would latch the throwaway flow for the life of the composition and the manga
selection chrome would never update again.

**The fix that would be right** (not applied — needs a device to validate, and there is already one
unverified change in flight): move both `init` blocks' launches behind an explicit `start()` called
from `MangaLibraryScreen` via `LaunchedEffect`, which matches the `ensureSeeded` doc comment's own
intent ("the moment this screen is reached" = the Manga screen, not the Library screen). Risk:
`ensureSeeded()` is the documented repair path for a membership wipe, so deferring changes *when*
repair happens; and `MangaLibraryViewModel` is constructed directly by `desktopApp/Main.kt:577` and by
tests.

Checked and dismissed: `FolioLibraryRoutes.kt:314`'s `navModel.mangaBrowseVM != null` also forces a
`by lazy`, and `!= null` on a non-null `lazy` is always true — a smell, but `BrowseViewModel`
(`MangaBrowseViewModel.kt:76`) has no `init` and only `Lazily` flows, so construction is cheap.

## MEASURED: the five cold-start fixes do nothing. Revert the hoist.

The device came back, so the five changes were finally measured instead of reasoned about. Full
write-up in `.dbg/ab/RESULT.md`; APKs kept at `.dbg/ab/prefix.apk` and `.dbg/ab/postfix.apk`.

**Method.** Built a genuine pre-fix APK (backed the 5 files up to `.dbg/ab/keep/`, reversed the
edits, `assembleRelease`, restored from the copies — *not* `git stash`, which would have reverted
the whole session's work), then measured both builds in one session, interleaved post → pre → post,
3 cold + 2 warm per batch.

**The trap that nearly invalidated it:** the installed app was `lastUpdateTime=17:22` while the
APK with the fixes was built at 18:30 — so the first run measured the *old* build. Always check
`dumpsys package <pkg> | grep lastUpdateTime` against the APK's mtime. Related: `prefix.apk` and
`postfix.apk` came out at **byte-identical size** (28512773) despite different code; only `md5sum`
distinguished them.

**Result — no measurable difference.**

| batch | cold avg | warm avg | ratio | cold worst | warm worst | worst ratio |
|---|---|---|---|---|---|---|
| post-fix #1 | 37.01 | 30.69 | 1.206 | 188.2 | 124.4 | 1.513 |
| **pre-fix** | 35.96 | 29.85 | **1.205** | 141.9 | 93.9 | 1.512 |
| post-fix #2 | 40.01 | 32.07 | 1.248 | 217.1 | 127.6 | 1.702 |

The ratio is the drift-free metric: everything in the session ran ~5ms slower than the morning
baseline, and cold moved +6.1ms while warm moved +5.6ms — the same amount, so it was device state
(the phone is now on USB power), not code. Pre-fix sits exactly where monotonic drift predicts,
between the two post batches. Ratio 1.205 pre vs 1.206/1.248 post → no benefit.

**And the mechanism didn't change either.** Frame-level, both builds still show *two* composition
events in the transition window, with total `recompose` of pre 94.1/101.1/87.2ms vs post
89.3/108.5/98.7ms — the same work. If the seed had removed the skeleton→grid swap, the second event
would be gone.

**Why the seed cannot work** — this is the part worth remembering. `LibraryViewModel.filteredBooks`
(`LibraryViewModels.kt:290`) ends in `combine(baseFlow, shelfBookIds) { … }`, and `combine` emits
**nothing** until *both* upstreams have emitted. `libraryVM` is `by lazy`, constructed by the
destination's own composition, so both reads start at that instant. The seed does hold the opening
frame (no skeleton), but `combine`'s first real emission lands one DB round-trip later (~25–30ms)
and recomposes the grid anyway. One composition is traded for another; the expensive part — the
grid — composes either way. Only the skeleton's composition is saved, which is cheap.

**The actual ceiling, unchanged by all of this:** `render` is 8.0–9.6ms per frame in *every* run,
cold and warm, both builds. At 90Hz the budget is 11.1ms, so render alone holds the transition at
~30fps. That is the Haze `hazeSource` capture paid twice. No composition-side change can fix it,
and the one lever (standing the backdrop down) was already reverted for a visible material flicker.

**Recommended:** revert `libraryBooks` + `knownBooks` (they add an app-lifetime eager DB
subscription — a second permanent subscriber on `allBooks()` — for no measured gain). Keep the
other three, which are independently defensible even though none moved the morph: the `remember`ed
shelf flows fix a real bug (`allBooks()`/`allSeries()`/`filteredBooks()` return a *new* Flow per
call, so inline use made `collectAsState` resubscribe — a fresh DB read per recomposition); accent
sampling on `Dispatchers.Default` moves a real ~10ms UI-thread read off the main thread; the
draw-phase cover reveal removes per-frame recomposition of every cover.

**Sources are restored to the fixed state on disk** (verified: `libraryBooks` ×3, `knownBooks` ×6),
so nothing is half-reverted. The revert is a decision, not a pending edit.
